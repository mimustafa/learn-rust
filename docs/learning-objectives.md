# Learning objectives

By Day 30, a learner can:

- Explain move, copy, borrow, aliasing, and lifetime rules and use compiler diagnostics to repair code.
- Model domain states with structs, enums, `Option`, `Result`, and validated newtypes.
- Choose functions, generics, and traits based on concrete API/testability needs rather than reflexively abstracting.
- Organize an idiomatic Cargo package with clear module visibility and dependency direction.
- Write unit and integration tests and use tests to make refactoring safe.
- Build a bounded HTTP API, validate input, use parameterized SQL, and handle errors without exposing internals.
- Distinguish async I/O from CPU parallelism, bound concurrency, and reason about cancellation and shared state.
- Instrument, benchmark, and profile before optimizing; discuss reliability and operational trade-offs.
- Explain the cost of a service boundary and defend a modular monolith when it is the simpler fit.
- Teach the ownership and architecture reasoning behind a feature to another experienced developer.

These outcomes describe practical competence, not mastery of every Rust ecosystem or a guarantee of production fitness.
